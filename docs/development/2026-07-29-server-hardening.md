# 2026-07-29 추가 17단계: 서버 업데이트와 호스트 보안

## 운영 점검

- 공개 `https://flow.mvtp.cloud`는 점검 시 HTTP 502를 반환했다.
- 리버스 프록시 서버의 Nginx와 SSH는 실행 중이고 실패한 systemd unit은 없었다.
- 리버스 프록시 서버의 UFW는 비활성 상태였다.
- 앱 서버는 작업 환경과 리버스 프록시 서버 모두에서 `No route to host`였고 3000/tcp health check도 연결되지 않았다.
- 앱 서버가 네트워크에 복귀하기 전에는 데이터 백업, 마이그레이션, 컨테이너 갱신을 안전하게 수행할 수 없다.

## 구현

- `APP_BIND_ADDRESS`를 추가했다. 기본값은 기존처럼 `127.0.0.1`이며, 별도 호스트의 리버스 프록시가 접근할 때만 앱 서버의 사설 LAN 주소를 명시한다.
- 호스트 역할별 UFW 계획/적용 스크립트를 추가했다.
- 프록시 역할은 SSH, HTTP, HTTPS만 허용한다.
- 앱 역할은 SSH와 지정한 프록시 IPv4/CIDR에서 들어오는 앱 포트만 허용한다.
- 적용 전에 `ufw show added`를 예상 규칙과 비교하며, 과거 허용 규칙이나 중복 규칙이 하나라도 있으면 변경 없이 중단한다.
- Docker published port의 UFW 우회를 막기 위해 원래 목적지 주소·포트를 conntrack으로 확인하는 `DOCKER-USER` 정책을 설치한다. 프록시 출처는 허용하고 나머지는 거부한다.
- Docker 재시작·호스트 재부팅 뒤에도 정책이 복원되도록 Docker 이후 실행되는 oneshot systemd unit을 설치한다.
- 기본 실행은 계획만 출력한다. `--apply`는 root, UFW/ss 존재 여부와 실제 SSH 포트 리스닝을 확인한 뒤에만 방화벽을 활성화한다.

## 복구 후 적용 순서

1. 앱 서버의 전원, NIC, 라우팅을 복구하고 프록시에서 SSH/3000 포트 도달 여부를 확인한다.
2. 운영 `.env`의 `APP_BIND_ADDRESS`를 앱 서버 사설 주소로 지정한다.
3. `backup-local-data.sh`로 DB와 업로드를 백업한다.
4. Compose 설정 검증과 마이그레이션 preflight 후 새 이미지를 배포한다.
5. 앱 서버에서 프록시 주소만 3000/tcp에 허용하는 UFW 정책을 적용한다.
6. 프록시 서버에서는 공유 중인 다른 서비스의 포트를 별도 확인한 뒤 프록시 역할 정책을 적용한다.
7. 내부 health check와 공개 HTTPS smoke test가 모두 성공하는지 확인한다.

서버가 오프라인인 상태에서 방화벽이나 배포 성공을 가장하지 않으며, 실제 적용 결과는 서버 복구 후 이 문서에 추가한다.
