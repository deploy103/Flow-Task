# 2026-07-29 추가 18단계: 서버 기본 보안 12개 항목

## 기준 대조

- 지정 문서의 12개 제목과 설명을 원문에서 다시 추출했다.
- 프록시 호스트의 SSH, UFW, 서비스 계정, TLS, Nginx, 파일 권한, AppArmor, 로그, Cloudflare, Fail2ban, 패키지 상태를 읽기 전용으로 확인했다.
- 확인 결과는 `docs/security-baseline-12.md`에 준수, 미준수, 부분 준수, 확인 필요로 구분해 기록했다.
- 앱 호스트는 프록시와 작업 환경 양쪽에서 라우팅되지 않아 확인 불가로 남겼다. 도달할 수 없는 서버를 준수로 판정하지 않았다.

## 발견 사항

- 프록시 SSH는 공개 키를 허용하지만 비밀번호 인증도 허용하며 사용자 제한이 없었다.
- UFW가 설치되지 않아 호스트 인바운드 기본 차단을 증명할 수 없었다.
- Cloudflare 프록시는 확인했지만 WAF managed rules 활성 여부는 호스트에서 알 수 없다.
- 자동 업데이트 서비스는 활성이나 적용 대기 패키지가 30개였다.
- 서비스 계정 권한, HTTPS 인증서, Nginx directory listing, 설정·로그 권한, 로그 수집·회전, Fail2ban jail은 확인 시점 기준을 만족했다. AppArmor 자체는 활성이나 Nginx/컨테이너별 enforcing profile은 확인하지 못해 부분 준수로 남겼다.

## 18-b 구현

- 12개 기준을 같은 순서로 반복 점검하는 읽기 전용 감사 스크립트를 추가했다.
- SSH 키 준비와 비밀번호 인증 차단을 두 단계로 분리했다. 키 fingerprint를 별도 로그인으로 검증해야 enforce 단계로 진행할 수 있다.
- root를 유지 사용자로 지정하지 못하게 하고, 유효 SSH 설정에서 실제 hardening 값이 반영됐는지 확인한다.
- SSH 설정 구문 검사, 유효 설정 검사, reload 중 하나라도 실패하면 기존 drop-in을 복원한다.
- 역할별 UFW 스크립트에 관리 VPN/CIDR만 SSH에 허용하는 옵션을 추가했다.
- SSH 사용자 제한과 UFW 출처 제한이 모두 있어야 감사 4번 항목을 통과하도록 했다.
- Fail2ban은 서비스 실행뿐 아니라 하나 이상의 jail이 있어야 통과하도록 했다.
- 감사, SSH, 방화벽 스크립트는 실제 호스트 설정을 바꾸지 않는 stub 기반 회귀 테스트로 성공·거부·원복 경로를 검증한다.
- 리뷰 피드백에 따라 UFW active 여부만 보지 않고 역할별 정확한 허용 목록과 대조한다. 예상 외 공개 포트, 중복 규칙, 전역 SSH 규칙을 모두 실패 처리한다.
- `apt-get -s upgrade` 자체가 실패하면 업데이트 0건으로 간주하지 않고 상태 확인 실패로 판정한다.

## 적용 보류

SSH 비밀번호 차단, UFW 활성화, 패키지 업데이트는 원격 접속 단절이나 다른 서비스 중단 가능성이 있는 운영 변경이다. PR 리뷰 전에 적용하지 않는다. 리뷰 후에도 사용자의 Ed25519 공개 키, 별도 키 로그인 성공, 실제 관리 VPN CIDR, 현재 공유 포트, 앱 서버 복구, 백업을 확인한 뒤 문서 순서대로 적용한다.
